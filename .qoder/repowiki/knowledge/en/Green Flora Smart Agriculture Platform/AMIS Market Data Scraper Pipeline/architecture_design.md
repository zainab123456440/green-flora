The module is organised as a four-layer Python package (`Scraper/`) with a single CLI entry point and clear dependency direction: `run.py` (argparse + logging) → `pipeline.run_pipeline` (orchestrator) → `parser` (HTTP scraping via `requests` + `BeautifulSoup`) and `db` (Supabase client via `supabase` SDK). `config.py` centralises all external constants (Supabase credentials, AMIS URLs, retry/backoff settings, table names, batch size) loaded from environment variables or a local `.env`. The pipeline follows a fixed ten-step sequence: connect to Supabase and discover schema columns at runtime, start an ingestion log row, discover commodities from the AMIS browse page, scrape each commodity's price table, normalise parsed `MarketPrice` rows, resolve foreign-key IDs for commodities/markets in Supabase, build rate row dicts, bulk upsert with batched `on_conflict` on `(commodity_id, market_id, price_date)`, then close the ingestion log with success/partial/failed status. Failure isolation is enforced per-commodity — one bad scrape never blocks others — while Supabase connectivity failures are fatal. A `--dry-run` mode skips all DB writes and prints a summary instead.
