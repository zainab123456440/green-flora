Two-layer design per domain: thin FastAPI routers (`routes/farmer.py`, `routes/field.py`) that validate payloads via Pydantic schemas, resolve the authenticated user_id through a shared `_resolve_user_id` helper (supporting DEMO_MODE bypass), and delegate all business logic to singleton service instances (`services/farmer_service.FarmerService`, `services/field_service.FieldService`). Each service encapsulates data access against Supabase tables (`farmer_profiles`, `farms`, `fields`, `crop_cycles`, `crops`) and switches between live DB mode and an in-memory demo cache based on `config.settings.demo_mode`. Ownership is enforced at the service boundary — fields and cycles are scoped to the user's farm via `_get_farm_for_user` plus `_verify_field_ownership` / `_verify_cycle_ownership` before any mutation. Auto-provisioning creates missing `farmer_profiles` and `farms` rows lazily on first access. The route → service → Supabase dependency direction is strict; routes never import `supabase` directly.
